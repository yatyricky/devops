# 类型化数据流工作流：删 apps//cli.js，原子能力 + 卡片式类型插槽编辑器

## 设计原则（已与用户对齐）

- **GUI 是唯一入口**：删除 `cli.js`（含 package.json 的 `cli` script），不留 CLI 冗余。
- **线性工作流，无 DAG**：步骤是有序列表；数据流靠"引用更早步骤的产出物"表达。
- **严格类型化数据流**：每个步骤声明带类型的产出物（outputs），每个参数是带类型的输入槽；类型不匹配的引用在编辑器里选不出来、保存时编译校验兜底（指名步骤+变量报错）。
- **插槽交互**：卡片 + 下拉（引用只列类型兼容项）；手动输入允许手打 `{{引用}}`，保存时校验。
- **apps/ 删除**，三个应用迁移为 `workflows/*.json`。

## 一、类型系统（engine/workflow.js 内实现）

类型集：`string`（纯文本）、`bash`（命令串）、`path`（本机路径）、`remote_path`（服务器路径）、`number`、`bool`、`list`、`map`。

**引用兼容表**（整值引用 `{{name}}` 时）：`string`←{string,number,bool}；`number`←number；`bool`←bool；`path`←path；`remote_path`←remote_path；`bash`←{string,number,bool,path,remote_path}；`map`←map；`list`←list。

**嵌入规则**（字面量里内嵌 `{{name}}` 时）：字面量整体取槽位类型；嵌入引用必须可渲染为文本——`string` 槽最严（path/remote_path/map/list 均拒绝，即"文件不能当字符串入参"），`bash`/`path`/`remote_path` 槽允许嵌 string/number/bool/path/remote_path。

- 产出物来源三类：步骤内置 outputs、`params`（string）、env 变量（类型由 envSchema 样例值推导：字符串/数字/布尔）。
- 运行时不变（仍渲染为字符串）；类型是编译期校验层，错误一次性全部报出（`步骤[3] upload.from 引用了 {{versionId}}（string），该参数需要 path` 格式）。
- 存储 JSON 格式不变（模板字符串），现有 SPA 工作流天然兼容。

## 二、引擎改造（engine/workflow.js）

1. **STEP_META**：每个步骤类型声明 `label`（中文）、`desc`、`params[]`（key/type/required/desc/itemType）、`outputs[]`（name/type/desc）；导出 `describeSteps()`，新增 `GET /api/step-types`。
2. **新增原子步骤**：`vars.set`（声明派生产出物：`{ pairs: { 名: 值 }, types: { 名: 类型 } }`）、`log`（`{ message }` 文本标注行）。
3. **各步骤类型标注**：checkout→versionId/buildTime/releaseName(string)；archive→archivePath(path)+archiveName(string)；upload→uploadedTo(remote_path)；template.push→uploadedTo(remote_path)；remote/shell 无内置产出（需要就接 vars.set）。
4. **参数槽位类型标注**：`env.write.file`=path、pairs 值=string；`shell.command`/`remote.command`=bash；`shell.cwd`、`archive.source`、`upload.from`、`template.push.template`=path；`upload.to`、`template.push.to`=remote_path；`template.push.vars`=map；`archive.entries/excludes`=list。
5. **迁移所需增强**：`archive.excludes` 改路径段匹配（任一层级命中即排除，如 node_modules）；`env.write.file` 支持模板渲染（写 `<clientDir>/.env`）；`template.push.template` 支持 `./` 前缀=相对工作流配置目录。
6. **编译器**：构建符号表（含类型），对每步每参数按上述规则校验，错误累积全量报出。

- **删除**：`apps/` 整目录、`cli.js`、package.json 的 `cli` script；`engine/release.js` 裁剪掉仅为旧模板流程服务的 `renderRemoteScript`/`uploadAndRunRemoteScript`/`printRemoteScriptForDryRun`（保留 `validateReleaseName`/`shellQuote`）。

## 五、三个应用迁移（依据 git HEAD 的 Ansible 逻辑转写）

模板放**各自应用仓库** `deploy/` 目录（遵循你定的原则；仓库不存在则回落 `workflows/<name>/` 用 `./` 引用）：

- `workflows/kids-ledger.json`（deploy/rollback/status/apply-config）：checkout → pnpm install/build → archive(server,shared,dist,package.json,package-lock.json) → upload → 远端解压+`pnpm install --prod`+state 数据软链+切 current+systemd 重启+健康检查（bash 重试循环）+旧 release 清理；模板从 HEAD `templates/kl/*.j2` 转写为 `{{DOMAIN}}/{{APP_PORT}}/{{SERVICE_NAME}}/{{SERVICE_USER}}/{{DEPLOY_DIR}}` 占位风格。
- `workflows/xlgbis-ls.json`、`workflows/xlgbis-bs.json`（各 6 任务）：deploy-client = checkout → env.write(`<clientDir>/.env`，VITE_* 映射) → pnpm -C build → archive(build) → 远端 client-release/ 切链+nginx reload；deploy-server = checkout → env.write(`<serverDir>/.env` 运行时键+VERSION 注入) → archive(server 目录+packages/common，段排除 node_modules 等) → 远端解压+两端 pnpm install --prod+权限修正+切 server 链+daemon-reload/restart+等 active+端口探活；apply-config = template.push 全套站点模板（ls：nginx-site/frps.toml/frps.service/nginx.service/xlgbis-login.service/frp_token/503.html；bs：nginx-site/frpc.toml/frpc.service/xlgbis-biz.service）+ sudo 安装步骤；模板从 HEAD `templates/ls|bs/*.j2` 与 `files/*` 转写。
- **如实标注的语义差异**：Ansible 的 rescue 自动回滚不做——失败即停，切链前的失败不影响现网，切链后用 rollback 手动恢复。
