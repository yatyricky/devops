# ssh.upload 权限回退方案

## 根因

`engine/nodes/remote.js` 的 `ssh.upload`：SFTP（putFile）以 SSH 登录用户直写目标路径。上传到 `/etc/nginx/sites-available/` 这类 root 目录时必然 `Permission denied`。SFTP 无法 sudo，所以引擎里必须走"暂存 + sudo 提权安放"。

## 方案：直写优先，失败自动回退（不加控件）

遵循 Symlink 先例（恒 `sudo -n`、需 NOPASSWD、无 widgets），**直写成功则行为与现在完全一致**（/opt 等用户目录不产生 root 属主副作用），仅直写权限失败时回退：

`ssh.upload` run 改为：
1. `mkdir -p 父目录`（登录用户）；失败 → 自动重试 `sudo -n mkdir -p`；再失败 → 抛两段错误。
2. 直写 `sshPut`；抛错时若消息含 permission/denied/EACCES/EPERM → 走回退；其他错误原样抛出（不掩盖）。
3. 回退：`mkdir -p /tmp/devops-upload-<rand>` → `sshPut` 暂存到该目录 → `bash -lc 'sudo -n install -m 644 <staged> <remotePath>'`（单命令，sudo 作用域无歧义）→ `rm -rf` 暂存目录（登录用户即可删，try/finally 保证失败也清理）。
4. install 失败时抛组合错误（sudo 错误 + 原始直写错误），日志明示走了哪条路：`[upload] sudo-install（直写 Permission denied）`。
5. `install -m 644` 语义说明：回退落盘的文件属主 root:root、0644——对 nginx sites-available 正确；直写路径不受影响。
6. 更新节点 desc；修正 `remote.js:14` 头注释残留的"上传自动清理"描述（与已裁定的"无 trap"矛盾）。

不改 widgets（卡片保持无控件）、不改 web 前端。

## 验证

- `tools/verify-dryrun.js` 新增断言（mock 会话，不连任何服务器，符合约束）：
  - 直写成功 → 不走 sudo；
  - putFile 抛 Permission denied → 命令序列含 `sudo -n install -m 644 /tmp/devops-upload-*/<basename> <目标>`，暂存目录被清理，返回 remoteFile；
  - putFile 抛非权限错误 → 原样抛出、无回退；
  - mkdir 失败 → sudo mkdir 回退被调用。
